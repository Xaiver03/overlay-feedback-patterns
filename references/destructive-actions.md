# 危险操作：确认、撤销与不可逆

大厂越来越少弹「确认删除」，不是因为不在乎数据安全，而是因为**把成本转嫁给了每一次正常操作**。真正的判据不是「文案里有没有删除二字」，而是**做错了要花多少代价恢复**。

## 1. 三档判定

```
这个动作做完之后：
├─ 能在一次点击内反悔，且反悔不产生外部副作用？
│    → 轻档：直接做 + Snackbar【撤销】。不弹确认。
├─ 不能反悔，但影响面只有这一条记录 / 这一个对象？
│    → 中档：Popconfirm（就地、一句后果）。
└─ 不能反悔，且影响面大 / 对外发出 / 涉及钱 / 批量 / 跨工作区？
     → 重档：AlertDialog（写清后果与范围，destructive 主按钮，禁 scrim，Esc=取消）
        极端档（删库、注销、清空整个工作区）：AlertDialog + 输入名称确认
```

**「影响面大」要能举证**：条数、金额、涉及的工作区数、是否已同步给第三方。举不出数就用低一档，别用高摩擦兜底。

## 2. 撤销（Undo）成立的工程前提

Snackbar + 撤销是**产品承诺**，不是 UI 决定。缺任何一条就别做撤销，回到确认框：

| # | 前提 | 不满足的后果 |
|---|---|---|
| 1 | **软删除**：数据行保留（`deleted_at` 或状态位），有真实恢复路径 | 撤销按钮点了什么也恢复不了 = 欺骗用户 |
| 2 | **保留期明确**：撤销窗口（ Snackbar 时长）之后进入回收站/待清理期，不是立刻物理清除 | 「已永久删除」的措辞与实现不符，是对外不实陈述 |
| 3 | **幂等**：撤销与重做可安全重试，不产生重复行或双份扣减 | 网络重试时数据翻倍 |
| 4 | **无外部副作用**：删除不会触发已发出的邮件、支付、申报、第三方写、Webhook | 撤销撤不回已经出去的东西 |
| 5 | **审计留痕**：删除与撤销**都**入留痕，且撤销不被记成一次「新增」 | 留痕链与真实历史分叉 |
| 6 | **下游一致**：报表、聚合、缓存、索引在撤销后能重算 | 撤销了但数字没回来 |
| 7 | **权限一致**：撤销用的是同一条删除权限，不额外开一个「恢复」口子 | 越权恢复 |

**批量删除的撤销要整批原子**：部分成功时不能显示「已删除 8/10，点击撤销」这种半撤销，除非撤销真的能回滚那 8 条。

## 3. 不可逆动作的界面义务

重档 AlertDialog 的写法要求（每条都可评审）：

1. **标题写后果，不写动作名**：「永久删除这 12 条凭证？」优于「删除确认」。
2. **正文写范围与不可逆性**：条数、金额、影响的工作区、能不能恢复、恢复要找谁。
3. **主按钮复述动词**：`永久删除 12 条` / `确认扣款 ¥8,420`。禁用「确定」「OK」「是」——它们把决策成本又推回用户。
4. **主按钮用 destructive 样式**（红/危险色），且**初始焦点在「取消」**。
5. **禁 scrim 关闭、禁右上角 X**；Esc 等价于「取消」。
6. **超危对象要求输入名称确认**：输入框要求逐字键入对象名（工作区名、公司名），匹配前主按钮禁用。这比任何措辞都有效，因为它强制用户读到对象。
7. **给出「哪些会被影响」的可展开清单**，而不是让用户自己去列表里数。
8. **执行中不给假反馈**：删除进行中按钮进 loading 且禁用，完成后用 Snackbar 报结果（这时撤销窗口才真正开始计时）。

## 4. 什么时候必须保留确认框（即使能撤销）

- 动作**对外可见**（发送给客户、提交给税局、发给第三方、公开发布）。
- 动作**涉及资金**（扣款、退款、转账、开票）。
- 动作**改变他人可见状态**（注销成员、转移所有权、撤销授权）。
- 动作**触发不可回收的资源**（销毁密钥、注销域名、删除备份）。
- 用户**刚做完一批高成本工作**且界面无法自动重建（清空筛选后的整表编辑）。

这四类里，撤销只能作为**补充**（「已提交，30 分钟内可撤回」），不能作为唯一保护。

## 5. 严禁

- **原生 `confirm()` / `alert()`**：样式失控、无法放后果说明、无法本地化、在 WebView/移动壳里直接弹系统 JS 对话框（体验破口最大的一档）、无法测焦点、无法做输入名称确认。全部要收敛到统一浮层原语。
- **用 Toast 报危险动作的结果而不给出口**：「删除失败」飘 4 秒消失，用户既不知道没删掉也不知道下一步。失败必须留在原地（区域 Alert 或行内）。
- **静默删除**：任何删除都必须有可见回执（Toast 或 Snackbar），成功也要。
- **把「确认」做成默认焦点**：键盘用户按回车就删了。
- **确认框里塞表单**：那是 Modal 任务，不是确认。
- **同一个动作在不同页面用不同档**：删除一条凭证和删除一批凭证的档位差异要由**规则**决定（条数/金额阈值），不能由页面作者临时决定。

## 6. 阈值建议（可按产品调，但必须写成规则）

| 条件 | 档位 |
|---|---|
| 单条、可软删、无外部副作用 | 轻（Snackbar 撤销） |
| 单条、不可软删 | 中（Popconfirm） |
| 2–9 条、可软删 | 中（Popconfirm + 显示条数） |
| ≥10 条，或含金额 > 0，或对外可见 | 重（AlertDialog + 范围说明） |
| 删除整个工作区/主体/账号/密钥 | 重 + 输入名称确认 |

阈值一旦定下，要落到**代码里的一个判定函数**（例如 `resolveDangerTier(action)`），由统一入口消费；写在文档里而代码里各页自判，等于没有规则。
